# 浏览器 Agent 诊断基线

这组固定的 10 个任务用于复现当前 Agent 的问题，并比较后续提示词、上下文、规划与模型改动。它不是训练集，也不是经过隔离的 held-out 泛化测试集。请勿把在这 10 个任务上的调优结果写成通用浏览器任务成功率。

基线只执行查询、导航和本地测试控件操作，不登录、不购买、不预订。System1 可选择本地 Laya 或云端 DeepSeek；text helper 配置保持不变。云端决策和文本生成可能产生 API 费用，云端模式会把页面内容及任务历史发送给 DeepSeek。基线不会把验收规则或预设字段值提供给模型。

## 运行方法

System1 下拉菜单也支持“云端 Jev”。在项目根目录 `.env` 的 `TYPESAFE_API_KEY=` 后填入 TypeSafe/Jev 密钥，重启网页服务后选择该选项。默认地址为 `https://api.typesafe.ai`、模型为 `jev-latest`，可通过 `TYPESAFE_BASE_URL`、`TYPESAFE_MODEL`、`TYPESAFE_TIMEOUT_SECONDS` 覆盖；`SYSTEM1_PROVIDER=jev` 可设为默认。Jev 一轮一次请求，返回真实选项概率，操作和目标沿用原仓库结构化接口；text helper 配置不变。无需启动本地 Laya 或读取其 tokenizer。Jev 服务端未公开最终编码上下文，界面展示实际请求而非声称与 Laya 最终序列一致。归档单独记录 `jev_calls`，计入 System1 总调用数，不冒充 Laya。密钥只在服务端使用，云端调用可能收费。

1. 启动本地 Laya 服务，并在项目根目录的 `.env` 中配置 Laya 地址和 text helper。密钥只在服务端使用。
2. 在项目根目录运行 `uv run jev`，打开控制台显示的本地地址，默认是 `http://127.0.0.1:8766`。
3. 选择“System1 决策模型”（本地 Laya／云端 DeepSeek／云端 Jev），打开“基线测试”，检查任务列表。重复次数默认为 `1`，可设置为 `1` 到 `10`。
4. 点击“运行全部”按顺序执行全部任务，或点击某个任务的运行按钮只执行该任务。默认“运行全部”是一批 10 个任务、每项 1 次，不是每项运行 10 次。
5. 在“运行记录”中选择“查看记录”，检查该次尝试的 Decision trail、模型输入与输出、独立验收结果和“观察步骤”截图。
6. 使用“保存结果与评估”查看保存位置；“历史批次”可以打开已有批次。结果同时保存在本地文件中，分享前先检查隐私内容。

删除历史批次：选中批次后点击菜单旁的红色“删除”按钮，确认批次编号和目录。此操作会永久删除该目录中的全部 trace、截图、汇总和评估文件，无法撤销；不是仅从列表隐藏。运行中或尚未结束的批次禁止删除，先停止并等待结束。删除成功后自动切换到可用批次，没有剩余批次时清空查看面板。越界路径及含符号链接／目录联接的批次会被拒绝。

重命名历史批次：选择批次后点击“重命名”，输入 1–80 字符的名称。名称写入该批次的 `summary.json`，下拉菜单显示“名称 · 批次 ID”。批次 ID、目录名及已有 trace 保持原样；运行中的批次不能重命名。

“观察步骤”、NEXT ACTION 和 Decision trail 联动：选择观察会显示基于该观察的首个 Laya 决策及输入输出；点击调用记录则切换到该调用决策前的观察。点击 text helper 时，NEXT ACTION 显示对应 Laya 的概率，下方显示 text helper 自己的输入输出。同一步数下的刷新或重试观察分别关联；最终观察如果没有后续模型调用，不显示其他步骤的概率。旧批次从事件日志恢复关联，不改写原始归档。

截图上的元素框使用当前所选观察的坐标和编号。悬浮右侧 indexed elements 列表会高亮对应框，移开后恢复该次决策选中的目标；标注开关可以隐藏或显示所有框。没有后续决策的最终观察仍显示元素，但不显示概率。截图或坐标缺失时不绘制相应标注，避免错误套用最新页面的位置。

任务串行执行，不并发操作同一浏览器。每次尝试使用新建的、由本程序管理的标签页，但共享现有 Chrome profile；不会全局清理 cookie、登录态或缓存。因此“新标签页”不等于“全新用户环境”。比较两个版本时应记录并尽量保持浏览器环境一致。

每次尝试的固定预算是最多 **30 个已执行动作、60 轮 System1 决策、300 秒（5 分钟）**。这些不是整个批次的总额度。截图、页面加载与模型调用也会占用时间；外部请求已经开始时，停止或超时不能撤回已经执行的浏览器动作，也不能取消已产生的 API 费用。

DeepSeek 采用条件式两阶段：先单独选择 operation；仅 CLICK、TYPE_TEXT、SELECT 再单独选择对应目标。两阶段共享同一页面观察与历史，合计一轮，最多 120 次 System1 阶段调用。TYPE_TEXT 选中字段后仍调用 text helper，因此可能共三次调用。Laya 保持一次请求包含多个问题、只消费选定操作目标的方式。

DeepSeek 的 user 消息现在直接使用 Laya v3 的完整解码序列，包含 `<bos>`、`<eos>`、`<mask>`。共享状态只有 `page` 和 `recent_actions`，没有 `elements`；页面正文截取前 1200 字符，候选描述压缩及 tokenizer 截断也与服务端一致。唯一额外提示词是 system 消息中的 JSON 返回格式要求，不添加行为规则。indexed elements 仍可作为界面元数据保存，但不会发送给 DeepSeek。

`LAYA_CONTEXT_CHECKPOINT` 必须指向 Laya 服务端加载的同一 checkpoint，默认相邻目录 `../laya-browser-git/v10s`；`LAYA_CONTEXT_MAX_OPTIONS` 必须等于服务器第三个启动参数，本项目默认 `999`。服务端不得另用与 checkpoint 不同的格式覆盖。只读取本地 tokenizer 和配置，不加载模型权重，也不请求 Laya 推理。缺少文件、不支持的格式、候选过多需要分块时明确报错，不悄悄使用近似上下文。修改 tokenizer/config 后需重启网页服务。trace 保存配置哈希及 Laya tokenizer 长度；此长度不是 DeepSeek 自身的计费 token 数，两种模型的 tokenizer 和聊天协议不同。

选择一轮 DeepSeek 决策后，输入和输出按“操作选择／目标选择”上下展示，默认展开；独立 HTTP request body 区域分别展示各阶段请求。无需目标调用、尚未发出、失败均明确区分。Decision trail 将同一轮的操作选择和目标选择合并为一条，显示合计调用耗时，任一阶段失败则标记失败；text helper 仍单独显示。原始 trace 和实际模型调用计数不合并。轮询不会重置同一记录的滚动和展开状态。

System1 在任务或批次开始时固定，不会中途换模型；下拉菜单对下一次启动生效。云端模式默认使用 `deepseek-flash`，关闭思考，仅输出各问题的选项编号，不调用本地 Laya。它复用相同的任务指令、NEXT_ACTION、TARGET、页面状态和候选集合，只增加 JSON 输出格式要求；这不代表两个模型的分词与推理模板相同。DeepSeek 没有返回选项分类概率，界面显示“概率未提供”，不伪造 100% 概率。TYPE_TEXT 仍单独调用原来的 text helper。

云端默认复用官方 DeepSeek text helper 的 `TEXT_MODEL_API_KEY`；也可单独设置 `SYSTEM1_DEEPSEEK_API_KEY`、`SYSTEM1_DEEPSEEK_MODEL`、`SYSTEM1_DEEPSEEK_BASE_URL` 和 `SYSTEM1_DEEPSEEK_TIMEOUT_SECONDS`。如果文本服务不是官方 DeepSeek 地址，必须提供单独的 System1 key，防止把其他提供商密钥发送到 DeepSeek。

### 强制停止规则

| 规则 | 当前上限与行为 |
| --- | --- |
| 无进展保护 | 最近连续 3 个动作均不是 WAIT，且每个动作前后的页面指纹均未变化时，以 `blocked` 停止。不要求点击同一个控件；这不是验证码等环境阻塞的证明。 |
| 动作预算 | 最多执行 30 个动作，拒绝第 31 个动作。点击、输入、选择、滚动和 WAIT 都计入；DONE/BLOCKED 不计动作，因此用完动作预算后仍可选择 DONE。 |
| 决策预算 | 最多开始 60 轮决策，不开始第 61 轮，失败轮次也计入。Laya 一轮一次调用；DeepSeek 一轮一至两次阶段调用，最多 120 次。text helper 单独计数；HTTP 传输重试不算新的决策轮。阶段之间检查取消、超时和页面新鲜度，失败不执行动作。 |
| 时间预算 | 每次基线尝试最多 300 秒，包含准备、观察、截图、模型调用和执行耗时。停止是协作式的，正在进行的调用返回后才在安全边界处理，因此实际耗时可能略超预算；不再发送下一次浏览器变更。 |

页面之间反复跳转会改变指纹，所以不会触发无进展保护，但仍受动作、决策和时间预算约束。连续 WAIT 也不会触发无进展保护，但每次 WAIT 占用动作预算。预算耗尽记为 `timeout`；无进展导致的 `blocked` 若不满足通过条件，通常记为策略失败。首次目标达成仅被记录，验收器不会代替 Agent 停止。

动作和决策上限由自由任务与基线共用；5 分钟的总时间限制仅由基线后台执行器实施。2026-09-29 起预算由 60 动作、120 次决策、600 秒减半；旧批次的 `manifest.json` 保留当时的预算，不改写历史结果。

点击“停止”结束当前批次，已保存的证据保留。程序重启后，未正常收尾的运行记为中断，不把它伪装成完成。不要在批次运行期间手动操作任务标签页；这会改变页面状态与测量结果。

## 十个固定任务

以下目标逐字对应任务注册表，不能为单次运行临时改写。地址以 `/` 开头时，使用当前本地演示服务器的 origin，不固定为 8766 端口。

### 01 从列表打开文章

- ID：`01_article_open`。
- 起点：`/fixture.html?scenario=research`，文章列表。
- 目标：`Open the article about using finite choices to control browser agents.`
- 通过证据：实际打开文章正文，标题为 `A browser is a choice, not a conversation`，正文含有限动作集合的内容，并停留在该文章。
- 反例：列表中出现匹配链接、打开另外两篇文章、打开正确文章后又返回列表，均不满足最终目标。

### 02 初始已经完成，直接停止

- ID：`02_article_already_open`。
- 起点：同一 Reading room 页面，由测试准备步骤先打开 `choices` 文章。
- 目标：`Open the article about using finite choices to control browser agents.`
- 通过证据：初始就有正确文章的标题与正文，Agent 选择 DONE，执行动作数为 **0**。
- 反例：即使后来仍在正确文章上，只要 Agent 执行过浏览器动作，也不满足本项的零动作要求；预测请求本身不是浏览器动作。

### 03 从错误文章恢复

- ID：`03_article_recover`。
- 起点：Reading room 的 `latency` 文章，即 `Where the milliseconds go`。
- 目标：`Open the article about using finite choices to control browser agents.`
- 通过证据：离开错误文章，最终打开有限选择主题的正确文章正文并停止。
- 反例：把任何文章详情都当作完成、只回到列表、只依据 URL 的 `#choices` 片段判断成功。

任务 02、03 的准备动作属于测试初始状态构造，不计入 Agent 成绩，也不是提供给策略的站点脚本。准备阶段实际点击本地 fixture 中的文章链接，并确认正文已渲染，不能只给 URL 加 hash。fixture 返回列表时可能保留旧 hash，所以三个文章任务均检查当前可见正文而非仅检查 URL。

### 04 查找英文维基词条

- ID：`04_wikipedia`。
- 起点：`https://www.wikipedia.org/`。
- 目标：`Find and open the English Wikipedia article about Alan Turing.`
- 通过证据：最终页面属于英文维基的 `/wiki/Alan_Turing`，主标题为 `Alan Turing`，并有可见的传记正文。
- 反例：搜索框里仅填入姓名、停留搜索结果、打开其他语言版或同名列表，都不通过。

### 05 百度搜索后停止

- ID：`05_baidu`。
- 起点：`https://www.baidu.com/`。
- 目标：`在百度搜索“华为官网”，停留在搜索结果页，不登录、不打开任何结果。`
- 通过证据：实际提交关键词 `华为官网`，百度 `/s` 结果页的查询参数对应关键词，并显示搜索结果。
- 反例：只填搜索框但未提交、打开搜索结果、点击登录，均不通过；打开结果后再返回，也不能抹除已记录的禁止动作。

### 06 滚动并进入第二页

- ID：`06_pagination`。
- 起点：`https://books.toscrape.com/`。
- 目标：`Go to page 2 of the book catalogue and leave that catalogue page open.`
- 通过证据：目录页显示 `Page 2 of ...`，且存在可见图书列表。
- 反例：只看到或点击 Next、留在第一页、进入单本书详情，都不通过。任务不强制某条滚动路径，验收最终目录状态。

### 07 修改并保持勾选状态

- ID：`07_checkboxes`。
- 起点：`https://the-internet.herokuapp.com/checkboxes`，初始状态必须是第一个未勾选、第二个已勾选；不符时报告准备失败，不静默改写状态。
- 目标：`Check the first checkbox. Leave the second checkbox checked without changing it.`
- 通过证据：两个控件的实际 `checked` 值均为 `true`，且没有操作第二个控件。
- 反例：第二个控件先取消再重新勾选，虽然最终画面相同，仍违反“保持不变”。验收检查布尔状态和已执行目标，而不是只读文字。

### 08 筛选住宿并打开详情

- ID：`08_travel_filters`。
- 起点：`/fixture.html`，默认住宿搜索页。
- 目标：`Search for stays in Lisbon, set the category to Design, enable Free cancellation, then open Casa Flora.`
- 通过证据：Lisbon 搜索确实已提交、类别是 Design、Free cancellation 已开启，最终打开 Casa Flora 的可见详情且对应 Lisbon。
- 反例：未提交搜索就打开原本可见的 Casa Flora、只填入 Lisbon、遗漏任一筛选，都不通过；详情本身匹配不能替代所要求的控件设置。

### 09 等待异步结果

- ID：`09_dynamic_loading`。
- 起点：`https://the-internet.herokuapp.com/dynamic_loading/2`。
- 目标：`Start loading and stop when “Hello World!” is visible.`
- 通过证据：执行过一次 Start，最终完成区域的 `Hello World!` 实际可见。
- 反例：点击 Start 后立即 DONE、仅存在隐藏文字、重复点击 Start，均不通过；不把 WAIT 次数当作加载完成证据。

### 10 携程多条件机票查询

- ID：`10_ctrip`。
- 起点：`https://flights.ctrip.com/online/channel/domestic`。
- 目标：`在携程查询 2026 年 12 月 20 日从北京到上海的单程经济舱直飞航班。看到符合条件的航班列表后停止，不登录、不选购或预订航班。`
- 通过证据：北京到上海、2026-12-20、单程、经济舱均能从查询状态与页面上确认，有实际可见航班列表，且直飞筛选或航班行证据表明满足直飞要求。
- 反例：只填好查询表单、只有日期而无航班、路线或舱位无法确认、登录、进入选购或预订流程，都不能通过。
- 边界：这是固定日期诊断任务，不自动改成“明天”；日期过期后应建立新版本。目标没有规定成人数量，不额外添加人数验收条件。携程的页面、区域版本、弹窗和风控可能变化，不能把选择器不适配判成策略成功。

## 验收原则

验收读取页面事实，不采用 Laya 的 DONE 判断作为成功证据。模型可以错误地 DONE，也可以在目标已达成后继续点击。初始观察、每次动作后的观察和最终观察均参与独立验收并保存截图；截图失败会留下错误信息，而不是生成一张替代图片。

每次尝试分别记录：

- 最终状态：正常结束时，目标是否仍然满足。
- 曾经达成：运行中是否至少有一次观察满足全部条件。
- 首次达成步骤：目标第一次成立时已执行了多少动作；初始页面已经满足时为第 0 步。
- 达成后额外动作：首次达成后仍执行了多少动作，帮助定位“不知道何时停止”。
- 提前停止：模型结束了任务，但页面证据尚不满足目标。
- 逐条件证据：哪些条件满足、不满足或无法确认，以及任何禁止动作的迹象。

“曾经达成”不等于最终成功。例如打开目标文章后又返回列表，应保留首次成功证据和额外动作数，并按最终页面记录失败。反过来，URL 中出现目标词、搜索框填入目标词、页面上存在一个匹配链接，都不能单独证明相应任务完成。

对网络拦截、验证码、强制登录或站点不可用，记录环境阻塞。页面结构变化导致验收器无法可靠读取证据时，记录无法判定，不随意记成功，也不混入普通策略错误。公开站点的验收器仍需要实际运行校验；文档与离线测试不代表携程或其他真实站点已经验证通过。

## 结果状态

| 尝试状态 | 含义 |
| --- | --- |
| `passed` | Agent 以 DONE 正常结束，独立验收确认最终目标满足，且没有禁止动作。 |
| `failed` | 能够进行验收，但最终目标未满足，或违反任务限制。 |
| `environment_blocked` | 验证码、强制登录、访问限制等环境因素阻止正常完成。 |
| `evaluation_unknown` | 缺少可靠证据或验收结构不适配，无法确认结果。 |
| `error` | 模型请求、浏览器或运行器发生异常。 |
| `timeout` | 本次尝试达到预算限制。 |
| `cancelled` | 用户停止了本次运行。 |
| `interrupted` | 进程退出或重启，使运行未正常收尾。 |

运行状态与验收证据分开保留。例如一次超时可以同时带有“曾经达成”的记录，便于区分一直未完成与完成后继续操作。

批次状态是 `completed`、`cancelled`、`error` 或 `interrupted`。`completed` 只表示本批次正常跑完，不代表每个任务都成功。应同时查看成功数、各类失败与阻塞数、动作数、调用数、耗时，以及达成后额外动作数。新批次用 `decision_rounds` 记录决策轮数，`decision_calls` 汇总已发起的 System1 调用（包括失败），并保留 `laya_calls`、`deepseek_calls`、`text_calls`。一轮 DeepSeek 可对应两个调用，不伪装成 Laya 调用。界面、CSV 和中文报告分别展示轮数与调用数；旧记录按原单次决策口径读取，不改写归档。`manifest.json` 的 `system1` 保存提供商、模型、地址和请求超时，历史批次没有此字段时视为 Laya。

## 保存的证据

每个批次写入 `artifacts/baselines/<时间戳>/`，界面显示本机的实际保存路径。尝试子目录是 `<任务ID>/attempt-01/`、`attempt-02/` 等。

| 文件或目录 | 内容 |
| --- | --- |
| `manifest.json` | 本次任务清单、重复次数、开始信息和可复现配置，不含认证密钥。 |
| `summary.json` | 结构化的批次与逐次结果，便于后续分析。 |
| `summary.csv` | 表格形式的逐次结果，便于比较不同版本。 |
| `report.zh.md` | 可直接阅读的中文结果与评估报告。 |
| 各任务/尝试目录中的 `events.jsonl` | 按顺序追加的运行事件，可用于检查中断前发生了什么。 |
| 各任务/尝试目录中的 `trace.json` | 完整 Agent 轨迹、模型请求与响应以及执行记录。 |
| 各任务/尝试目录中的 `evaluation.json` | 初始、动作后和最终的验收条件、证据与结果。 |
| 各任务/尝试目录中的 `screenshots/` | 每次成功截图对应的图像；失败原因保留在 trace 与事件记录中。 |

密钥、认证请求头和 `.env` 不进入导出。但页面文字、URL、输入值、模型上下文和截图可能包含个人信息，不能把“不保存密钥”理解成“所有运行数据都不敏感”。不要未经检查就提交或公开 `artifacts/`。

## 如何比较改动

先保存当前版本的一批结果作为基线，再在相同任务、重复次数和浏览器环境下测试修改后的版本。一次只比较一类变化，例如提示词、完成判断、上下文压缩或模型 checkpoint，避免同时改动后无法归因。

优先检查任务级最终结果和具体失败原因，再查看动作准确率、额外动作、调用量与耗时。真实网站会变化，单次通过不等于稳定；重复运行可帮助发现波动，但共享 profile 仍可能影响后续结果。用于开发诊断的任务与轨迹以后如果进入训练或提示词调优，就不能再声称它们是未见测试数据。
